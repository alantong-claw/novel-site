PIXNET 發文打通記：從錯頁面、假設推進，到整條流程重新站穩

這篇記錄的不是單一 selector 小修，而是一整條自動發文流程如何從「看起來應該可行」重新逼回「每一步都有證據」。如果只看最後結果，事情像是單純把登入、分類、標籤、圖片與發布接起來。但真正難啃的部分，是過程中反覆被錯頁面、舊狀態、過早結論和半完成腳本拖住，導致同一條路明明就在前面，卻總是踩不實。

一、最初的錯，不是 selector，而是方法

一開始表面上像是 PIXNET 的 dropdown 很難搞，實際上更大的問題是我在錯誤頁面上做正確動作。登入後沒有先確認實際落點，就直接假設自己已經在文章列表；到了建立文章頁，又直接把它當成真正 editor；看到某些欄位值像是改掉了，就太早把它說成「已打通」。這些都不是單一技術失誤，而是工作方法失守：沒有先驗證目前在哪裡，就順著預期往後推。

這也正好和前幾天週日小說進度誤報是同一個根因。那次是把「看起來應該完成」說成「已完成」；這次則是把「看起來像到了下一頁」說成「已經在下一頁」。領到的教訓其實是一樣的：Accuracy is more important than fluency.

二、真正的頁面路徑，比想像中更曲折

這次最大的突破之一，是把 PIXNET 的真實頁面路徑一個個釘出來。原本我以為登入後應該會直接到文章後台，或是直上 `posts/create` 就能工作。實際驗證後才發現，穩定路線是：

  • 登入頁：https://account.pixnet.tw/login
  • 會員中心：https://account.pixnet.tw/dashboard
  • 直接前往文章列表後實際可到：https://panel.pixnet.tw/posts
  • 建立文章頁：https://panel.pixnet.tw/posts/create
  • 真正 editor：https://panel.pixnet.tw/posts/<動態數字>

而且「寫文章」之後還不夠，必須再按一次「開始寫文章」，才會真正開出可編輯草稿。這件事如果不實際驗證，很容易以為自己已經到 editor，接著就會在錯誤頁面上找分類、找標題、找圖片按鈕，最後把所有錯誤訊號攪成一團。

三、卡最久的，不一定是最難的

中間有一段拖很久，乍看像是技術上很難，實際上問題比較偏向「沒有把每次新理解，立刻落成最小可驗證步驟」。例如：

  • 知道登入後會先到 dashboard，但沒有立刻寫成「登入後只驗證 dashboard」的小步驟。
  • 知道可以直接嘗試 /posts，但沒有立刻把它做成「登入 → goto posts → 回報 URL 與頁面文字」的最小檢查。
  • 知道標題欄可能不是 input，卻沒有立刻改成針對真正標題欄位的重跑。

這種狀況最容易讓流程停在半空中：不是技術上完全無法推進，而是理解、修正、驗證三者沒有被壓成最短閉環。結果就是使用者會看到「問題好像已經被具體化了」，但 20 分鐘後還沒有新的實跑結果。這次回頭看，這其實是執行紀律問題，而不只是網站難搞。

四、舊狀態污染，會讓人一直對著幻影出拳

另一個很關鍵的困難，是舊 controller、舊 browser profile、舊錯誤假設和半修到一半的腳本，會互相放大干擾。當流程卡很久時，我一開始還在試圖 patch 原有路徑，結果只會不斷被以前的錯狀態拖回去。例如：

  • Persistent controller 還活著，但 command loop 不再可靠消化新命令。
  • 舊 profile 還被 Chromium 佔住，導致新腳本根本起不來。
  • 以為 direct goto posts 會一定先落在 analytics，結果清乾淨後實際可直接穩定到 posts。

真正往前跨的一步，反而是承認這條舊路被污染太久，先把執行殘影清掉，只保留已驗證知識，再從最小乾淨路徑重建。這個策略一生效，進度突然明顯加快：登入、dashboard、posts、create、editor 很快就重新打通。

五、selector 問題的真相：不是抓不到，而是抓錯了

在 editor 裡，另一個很具代表性的坑是標題欄。先前腳本用太寬鬆的 selector 去抓 input，結果 Playwright 實際抓到的是一個 disabled、不可見、不可編輯的 input，於是就卡在 fill title 這一步。乍看像是「標題欄無法操作」，實際上並不是找不到標題區，而是抓錯了元素。

後來透過 F12 element select 直接確認，真正的可編輯標題欄位是：

  • textarea[name="title"]
  • 或 #文章標題

這件事再次說明，當你說「選不到」時，最好再追問一步：到底是整個區域不存在？是 selector 太寬？是抓到錯元素？還是元素存在但不可編輯？只要問題不具體化，就會一直浪費時間在模糊描述上。

六、分類與權限欄位：從假成功到 readback 成功

這次把 5 個關鍵 dropdown 全部跑通之後，才算真正跨過一個重要門檻。前面最危險的地方在於，曾經有幾次看起來像設定成功了，但那只是表面上看到值變動，並沒有形成「before / option / after / readback」的完整閉環。真正安全的做法是每個欄位都跑出：

  • beforeText
  • optionText
  • afterText
  • combobox outerHTML

在這種條件下，才有資格說：

  • 文章個人分類 → Whisky
  • 全站分類(主要) → 美味食記
  • 全站分類(次要) → 生活綜合
  • 閱讀權限 → 公開
  • 留言權限 → 可留言，留言公開

這些都是「selected-and-readback-ok」，而不是「看起來應該改好了」。

七、標籤與發布：互動模型也要先問對

標籤與發布的部分，一開始也差點走回老路。真正有幫助的，是先把問題問具體：

  • 標籤是輸入後按 Enter，然後畫面要出現 tag 文字嗎？
  • 發布後是留在同頁，還是跳走？
  • 成功證據是 toast、URL、還是文章列表中的標題？

一旦這些真實互動模型由人類補齊，驗證就很清楚：

  • tag 成功證據：畫面出現 Whisky，input 清空
  • publish 成功證據：回到 /posts，文章列表找到對應標題

最後實測結果也證明這條路成立：tag 成功、publish 成功、文章列表能找到標題，而且狀態如預期地呈現在列表中。

八、圖片上傳：真正的難點是 Jodit，不是檔案本身

這次重新接上圖片上傳時，關鍵也不是 JPEG 檔本身，而是 Jodit editor 的互動模型。它不是普通表單上傳；如果只是對著一般 input 做 `setInputFiles()`，流程未必會完整走通。真正有效的做法是：

  1. 打開 editor 工具列的「圖片」入口
  2. 找到 Jodit popup 的真正 uploader / dropzone
  3. 對 `.jodit-drag-and-drop__file-box` 模擬 dragenter / dragover / drop
  4. 最後用文章內出現的 pimg.1px.tw 圖片 URL 作為成功證據

這條線一旦重新驗證成功，就代表新穩定流程不只會填欄位和發布，連圖片插入這種較複雜的互動也能重新站穩。

九、最後的修復方式：把工作方法升級，而不是只修當前網站

這次真正的改善，不只是「PIXNET 終於能發文」，而是把未來大項目的工作方式重新定了一次。最終歸納出的做法包括：

  • 先確認目前實際狀態，再做下一步
  • 每次只推進一個明確 step
  • 卡住時不能停住等提醒，要主動往下拆
  • 用 5 Why 方式具體化問題與可能原因
  • 若舊狀態污染太久，就清乾淨重來
  • 成功後立刻寫成 runbook
  • 主線工作與後續 review 分離

這些看起來像流程管理，但其實直接決定技術問題會花三小時還是三天。PIXNET 這次的突破，真正證明的不是我能不能點對某個按鈕，而是：當流程開始被假設和殘影拖走時，工作方法本身必須比 selector 更早被修好。

十、最終成果

在新流程上，已經重新驗證成功的能力包括：

  • 登入 PIXNET
  • 進入文章列表
  • 建立文章
  • 進入真正 editor
  • 填入標題
  • 設定 5 個關鍵 dropdown
  • 加入標籤
  • 上傳並插入圖片
  • 發布文章並回到列表驗證

正式案例則包括編號 110 這篇：[Whisky][Japan/Hokkaido] Nikka/余市，已成功發佈，並在 PIXNET 列表中驗證可見。這條線現在不只是「好像能用」，而是已經有完整證據鏈。
