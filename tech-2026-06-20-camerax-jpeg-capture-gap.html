2026-06-20｜CameraX / ImageProxy / JPEG vs YUV / Save Path

為什麼 preview 正常、快門會動，照片卻還是存不下來

這次 BWCamera 的 bug 很適合留下來，因為它長得很像儲存問題，實際上卻死在儲存之前。表面症狀是：app 可以打開、preview 正常、濾鏡可見、按下快門也有反應，但照片始終沒有進相簿。若只看最後結果，很容易先懷疑 MediaStore、權限或某台手機的相容性；但真正的斷點其實在 ImageProxy 轉 bitmap 這一層。

一、問題的表象：拍照有走，存圖沒落地

當時的行為是：

  • Camera preview 正常。
  • UI 裡的黑白濾鏡、亮度、雜訊等控制可用。
  • 按下快門後，狀態看起來有進入拍攝流程。
  • 但最終沒有可見照片落到相簿。

這代表 bug 很可能不是「相機完全沒拍」，而是拍完之後某一段後處理或儲存鏈路沒有走完。

二、關鍵誤判：把 preview 的資料格式，偷渡成 capture 的資料格式

這個 app 有兩條影像路徑：

  1. Preview analyzer：用 ImageAnalysis 持續吃畫面，做即時黑白預覽。
  2. Still capture：用 ImageCapture.takePicture(... OnImageCapturedCallback ...) 在快門時抓一張高品質影像，再套濾鏡並寫入 MediaStore。

我原本的 bitmap 轉換函式 toNormalizedBitmap() 是沿著 preview 路徑長出來的，所以只處理 YUV_420_888。這在 analyzer 上完全合理，因為 preview 那條確實一直是 YUV。問題是，我把這個假設不小心帶進 still capture 了。

三、真正 root cause：CameraX 的 capture callback 回來的是 JPEG

這次關鍵在於：ImageCapture.takePicture(... OnImageCapturedCallback ...) 回來的 ImageProxy，預設不是 YUV，而是 JPEG。所以當 capture success 發生時，流程其實是：

  1. 快門 callback 成功進來。
  2. 呼叫 image.toNormalizedBitmap()。
  3. 因為函式只接受 ImageFormat.YUV_420_888，所以直接回 null。
  4. 後面的黑白處理、旋轉補償、saveBitmapToMediaStore() 根本沒有跑到。

也就是說，使用者看到的是「照片不能存」，但實際根因是「capture buffer 在轉 bitmap 前就被錯誤格式判斷擋掉」。

四、為什麼這種 bug 容易誤導

這種錯最麻煩的地方在於，它會製造一個很像儲存層故障的假象：

  • preview 沒問題，讓人以為影像格式處理整體是對的。
  • 快門有反應，讓人以為 capture 也成功了。
  • 相簿沒新照片，直覺就會把鍋甩給 MediaStore 或權限。

但只要把整條鏈路分段驗，就會發現：真正該問的不是「為什麼存不下來」，而是「存圖函式到底有沒有被呼叫到」。這次答案是否定的。

五、修法：同一個 normalizer 同時支援 YUV 與 JPEG

最後採取的修法很直接：保留原本的 YUV 路徑，另外補上 JPEG 分支。

  • YUV 分支：沿用既有 YUV_420_888 -> NV21 -> JPEG bytes -> Bitmap 的流程。
  • JPEG 分支：直接從 planes[0].buffer 取出位元組，交給 BitmapFactory.decodeByteArray() 解碼。
  • 共用後處理：兩條分支最後都走同一套 rotation、Sony 特例補償、直向正規化流程。

這樣做的好處是，preview 與 capture 雖然原始格式不同，但可以在 bitmap 階段重新匯流，後面的黑白濾鏡、旋轉補償與存檔邏輯就不需要各寫一份。

六、實作上的判斷：不要急著把責任分散到多個模組

理論上，也可以把 preview 和 capture 拆成兩套完全不同的 normalizer。可是對這個 app 當前的規模來說，那樣會把問題藏得更深。這次更好的做法，是讓 ImageProxyBitmap.kt 明確承擔一件事：把不同來源格式的 ImageProxy 正規化成同一種後續可處理的 bitmap。格式差異在這裡結束，不要往後滲透。

七、驗證結果

修正後，debug APK 已重新 build，且 Alan 實測回報這版 OK。這代表至少在目前 Sony 實機上，capture buffer 的格式差異已不再阻斷拍照存圖流程。

八、這次該記住的教訓

  • Preview pipeline 的資料格式，不可直接假設等同 still capture pipeline。
  • 當使用者回報「不能儲存」，要先確認 save path 是否真的有被執行到。
  • 在 CameraX 這類多 use case 並存的場景，最容易漏掉的不是 API 名字，而是同一個 ImageProxy 在不同 use case 下可能長得不一樣。
  • 真正可交付的成功判準，不是 UI 看起來能拍，而是最後那張照片真的留下來。

九、結語

這不是一個大張旗鼓的底層 crash，也不是什麼玄學手機相容性問題。它只是兩條各自合理的影像路徑，在資料格式交界處沒有接好。但也正因為它夠普通、夠像「應該不會吧」，才更值得記。未來再看到 preview 正常、快門正常、結果卻沒有產物時，第一反應不該只看最後一層儲存 API，而要回頭問：這張影像到底有沒有真的活著走到存檔之前。
