2026-05-05｜Context Budget / Workflow Design / Memory Architecture

把內容節省做成結構，不靠意志力硬撐：我們降低 content 使用量的演進

如果只看最後留下來的規則，會很容易以為「降低 content 使用量」只是後期做的一點節流優化。但回頭整理後比較清楚的結論是，這其實不是單一技巧，而是一條逐步收斂的工程路線。它從事故經驗開始，經過任務切分，最後延伸到長期記憶結構本身。

一、起點不是優化慾望，而是被 token 耗盡打到

這條線最早的背景之一，是 2026-03-24 曾經發生 token 用量耗盡，直接讓流程中斷。這件事的重要性，不在於單次失敗本身，而在於它把一個原本容易被忽略的事實變得非常具體：上下文不是免費的，而且當它失控時，流程會真的停下來。

很多時候人會把 context 視為一種模糊成本，覺得只是回應稍慢一點、字多一點。但當它真的造成中斷後，問題的性質就變了。從那一刻開始，壓低 content 使用量不再只是美化系統，而是直接關係到流程能不能跑完。

二、第一層收斂：把任務切成單篇、低 context、獨立完成

到了 2026-04-09，這個壓力開始轉化成明確工作策略。當時的調整不是單純提醒自己「少講一點」，而是直接改變任務結構：改成單篇、低 context、每篇獨立起 editor、成功一篇再做下一篇。

這樣的設計有三個直接效果：

  • 把失敗成本限制在單篇任務內，不會一篇卡住拖垮整批。
  • 每次工作只帶入當前需要的上下文，避免越做越肥。
  • 驗證邊界更清楚，單篇成功與否不會淹沒在整批長流程裡。

這很像把一條容易崩的長鏈，改成一串可以逐段確認的小節點。從 content budget 的角度看，它的關鍵不是「每次少載一點」，而是不要讓任務天然長成必須載很多東西的樣子。

三、第二層收斂：把高頻記憶與低頻規則拆開

再到 2026-04-18，優化方向已經不只停在任務流程，而是開始改長期記憶架構。那次做的核心調整，是把記憶檔拆分，讓 `MEMORY.md` 保留常載入的核心摘要，而把流程規則、做事準則和其他細節搬到別的檔案。

這個變化很重要，因為它代表系統開始承認一件事：不是所有記憶都值得用相同頻率進場。高頻、會反覆影響決策的內容，應該留在最短、最穩的核心層；低頻、只在特定工作才需要的規則，則應該按需載入。

這本質上就是 context budget management。不是等每次快超量了才緊張刪字，而是先把記憶分層，讓「常用的短、少用的深」成為結構預設。

四、這幾步其實在做同一件事：失敗隔離

乍看之下，token 耗盡、單篇處理、記憶拆分像是三件不同的事，但它們其實都在處理同一個核心問題：不要讓過多上下文綁在同一個失敗半徑裡。

  • 當流程太長，任何一步出錯都會讓整串任務受影響。
  • 當記憶太厚，每次啟動都要背著大量未必需要的內容前進。
  • 當規則、摘要、歷史細節全混在一起，系統就很難做到真正的按需取用。

所以後來形成的方法，不是孤立地「省 token」，而是同時設計任務邊界、記憶分層和失敗隔離。當這三件事一起做，content 使用量自然會下降，而且下降得比較穩，不需要每次都靠人硬撐。

五、真正有效的節省，不是克制，而是結構化

這段演進最後留下來的最重要結論是：如果一個系統需要不斷靠操作當下的自我克制，才能勉強控制 content 使用量，那它多半還沒有設計好。真正穩的做法，是把節省變成結構結果。

也就是說：

  • 任務預設就應該能局部完成，而不是必須綁成巨型長流程。
  • 記憶預設就應該分層，而不是每次全量進場。
  • 規則預設就應該按需讀取，而不是和高頻摘要擠在一起。

一句話總結，這條路的重點不是「少放點內容」，而是把任務邊界、記憶結構和失敗半徑一起收斂。當結構對了，省 content 會變成自然副產品，而不是額外負擔。
